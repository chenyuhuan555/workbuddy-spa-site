# 简历版本 AI 提取与排版设计

## 目标

修复 WorkBuddy V2 人才入库后把 PDF 原始提取文本误当成电子简历的问题。每个简历版本分别保存原始文本和 AI 排版文本；人才与原始文件先可靠入库，再由浏览器后台完成基础信息提取、候选人画像提取和电子简历排版。AI 不可用或处理失败时必须向用户显示原因，并允许对既有简历重新处理，无需重新上传。

## 范围

本次包含：

- V2 人才批量上传和单份上传的简历版本数据模型。
- V2 人才详情中的电子简历展示、状态与重新处理入口。
- 浏览器内串行 AI 处理队列及刷新恢复。
- 旧简历版本的兼容读取。
- 对已入库简历进行非破坏性重新提取与排版。

本次不包含：

- 新增服务端任务队列或后台服务。
- 删除、替换或重新编码原始简历文件。
- 修改推进记录、公司、岗位、负责人、分类、备注或其他业务历史。
- 批量重写所有历史简历。旧记录由用户按需重新处理。

## 现有问题

V2 上传流程提取 PDF 文本后将其直接存入 `resumeVersion.rawText`。PDF 提取阶段会压缩空白，因此该文本通常是一整段。人才详情页又优先把 `rawText` 当作“电子简历”展示，导致页面虽然有文字，却没有章节、列表和结构化排版。

代码中已有基础信息提取、候选人画像提取和电子简历 Markdown 排版能力，但 V2 上传流程只尝试基础信息提取，且异常被静默回退；画像和排版没有接入 V2 简历版本。用户无法区分“原始文字已提取”“AI 正在处理”和“电子简历已完成”。

## 方案选择

采用浏览器后台任务队列：原文件、原始文本和人才记录先入库，AI 任务随后串行执行。该方案符合当前 GitHub Pages 静态架构，不引入后端依赖，同时避免 AI 超时让用户误以为文件上传失败。

不采用上传阻塞方案，因为三项 AI 调用可能耗时或失败；不采用服务端任务队列，因为它需要新增服务端架构、鉴权和运维能力，超出本次范围。

## 数据模型

每个 `resumeVersion` 保留现有元数据，并增加以下字段：

```js
{
  rawText: '',
  formattedText: '',
  formatStatus: 'queued', // queued | processing | done | failed
  formatError: '',
  formattedAt: ''
}
```

字段语义：

- `rawText`：PDF、OCR、TXT 或 Word 解析得到的原始文字。它是重新处理的输入，不因 AI 成功或失败而改变。
- `formattedText`：AI 生成的 Markdown 电子简历，只保存排版后的正文。
- `formatStatus`：当前简历版本的排版状态。
- `formatError`：用户可见的失败原因。成功后清空。
- `formattedAt`：最后一次成功排版时间。

人才对象继续保存结构化字段，如 `name`、`currentCompany`、`currentTitle`、`city`、`summary`、`keywords`、`profileText` 和 `trajectory`。另增加人才级 AI 状态：

```js
{
  profileProcessStatus: 'queued', // queued | processing | done | failed
  profileProcessError: '',
  profileProcessedAt: ''
}
```

简历版本和人才结构化字段职责分离：版本字段描述某一份简历；人才字段描述当前人才画像。

## 兼容规则

- 旧版本没有 `formattedText` 时不修改其 `rawText`，并视为尚未排版。
- 旧版本缺少状态且有 `formattedText` 时视为 `done`。
- 旧版本缺少状态且只有 `rawText` 时视为可重新处理的 `queued` 状态，但不在页面加载后未经用户动作自动批量调用 AI。
- 现有 `fileId`、`sourceResumeId`、`fileHash`、`fileSize`、`fileType`、`uploadedAt` 和 `id` 原样保留。
- 不进行破坏性数据库迁移，不删除 IndexedDB 数据库或原始文件记录。

## 上传与后台处理流程

### 第一阶段：可靠入库

1. 读取文件并保存原始文件到现有 IndexedDB 文件存储。
2. 提取 `rawText`。
3. 创建人才和简历版本，简历版本状态设置为 `queued`。
4. 保存 Workbench V2 快照。
5. 页面立即显示“已入库，正在后台处理”。

只要第一阶段成功，AI 失败不得把该任务改成上传失败，也不得移除人才或原始文件。

### 第二阶段：浏览器后台 AI 任务

同一浏览器中使用串行队列，按以下顺序处理：

1. 基础信息提取：姓名、当前或最近公司、职位和城市。
2. 候选人画像提取：摘要、关键词、画像正文和职业/教育轨迹。
3. 电子简历排版：生成 Markdown 并写入当前版本的 `formattedText`。

每一步完成后立即持久化，避免后续步骤失败时丢失前一步结果。任务结束后触发既有云端同步排队。

新上传时，基础信息只补充空字段，不覆盖顾问已经输入的非空字段。画像字段属于 AI 派生字段，可以由本次处理结果更新。

### 刷新恢复

- `queued` 任务在具备 AI 权限和有效配置时可继续处理。
- 页面刷新前处于 `processing` 的任务恢复为 `queued`，避免永久卡在处理中。
- 自动恢复只处理本次或中断的明确队列，不扫描并自动消耗全部历史旧数据。
- 没有 AI 权限或配置时保持可恢复状态，并显示明确原因。

## 重新提取并排版

人才详情的简历页在当前版本旁提供“重新提取并排版”按钮。执行时：

1. 优先复用当前版本的 `rawText`。
2. 若 `rawText` 为空，则从当前版本的 `fileId` 或兼容原文件引用读取原文件并重新提取文字。
3. 不创建新的简历版本，不改变当前版本 ID 和原文件引用。
4. 重新运行基础信息、画像和排版。
5. 只更新当前版本的 `rawText`（仅原来为空时）、`formattedText`、格式化状态，以及人才的 AI 派生结构化字段。
6. 姓名、公司、职位和城市只补空值，不覆盖非空人工数据。
7. 不修改推进记录、备注、负责人、分类、其他简历版本或业务历史。

因此，雷艺旋现有简历可直接重新处理，无需重新上传 PDF。

## 展示与交互

电子简历区域按以下优先级显示：

1. `formattedText`：使用现有安全 Markdown 渲染器显示。
2. `processing` 或 `queued`：显示处理中状态和简短说明；如果已有旧排版结果，可继续显示旧结果直到新结果成功。
3. `failed`：显示可见错误信息、“重新提取并排版”按钮，并在下方以“原始提取文本”明确标识 `rawText` 降级内容。
4. 旧数据只有 `rawText`：显示“尚未进行 AI 排版”，提供处理按钮，并展示标明身份的原始文本。
5. 两种文本都不存在：显示无可用文本，并提示原文件是否仍可读取。

按钮使用 `type="button"`，处理中禁用并提供文字状态。错误提示使用可读文本，不只依赖颜色。

## 错误处理

以下错误必须在人才详情或上传任务中可见：

- 当前账号没有 AI 权限。
- DeepSeek API Key 未配置或无效。
- AI 请求超时、网络失败或返回格式错误。
- 原文件不存在且 `rawText` 为空。
- PDF/OCR 提取文本过短或不可用。

错误不得被只写入 `console.warn` 后静默忽略。错误状态持久化，但用户重新处理时先清空旧错误；再次失败则写入最新原因。

## 安全与数据边界

- AI 输入只使用当前简历的文本和必要候选人上下文。
- 不在日志或错误提示中输出 API Key、认证令牌或完整简历正文。
- 不把原始 PDF 二进制重新写入 Workbench 快照；继续使用 IndexedDB 外部文件存储。
- 更新通过现有 `saveWorkbenchV2()` 和保存协调器串行持久化，避免旧快照晚于新结果落盘。
- 重新处理不得调用删除数据库、删除文件或删除业务实体的接口。

## 测试与验收

### 数据模型测试

- 新简历版本同时支持 `rawText` 和 `formattedText`。
- 序列化、校验和重新加载后两个字段及状态完整保留。
- 旧版本只有 `rawText` 时仍可读取，且不会被误标为已排版。

### 流程测试

- 上传在 AI 调用前完成原文件和人才持久化。
- AI 三步按顺序执行，每步结果分别保存。
- AI 失败不会删除人才、简历版本或原始文件引用。
- 无 AI 权限、缺少 Key 和调用失败均产生用户可见状态。
- 刷新后中断的 `processing` 状态可恢复为可重试状态。

### 展示测试

- 有 `formattedText` 时优先显示它而非 `rawText`。
- 只有 `rawText` 时明确标记为原始提取文本。
- 失败时显示错误和重新处理按钮。
- 重新处理按钮有明确类型、禁用态和状态文本。

### 非破坏性测试

- 重新处理前后，版本 ID、`fileId`、文件哈希、上传时间、其他版本和推进记录保持不变。
- 人工维护的非空姓名、公司、职位和城市不被 AI 覆盖。
- 雷艺旋这类已有原文件或 `rawText` 的记录无需重新上传即可处理。

### 完成标准

- 针对新增行为的测试先失败、实现后通过。
- 完整测试套件与生产构建通过。
- 浏览器中验证上传、后台状态、失败状态、重新处理和排版结果。
- 部署后验证线上脚本版本和实际页面行为，不能只以 GitHub Actions 成功作为上线依据。
