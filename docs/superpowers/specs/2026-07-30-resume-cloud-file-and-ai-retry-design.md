# 简历原件跨设备同步与 AI 分阶段重试设计

## 背景

WorkBuddy 当前已经把候选人、简历版本元数据、`rawText` 和 `formattedText` 放入共享工作区，但新上传的原始 PDF、Word 或图片文件只写入上传设备的浏览器 IndexedDB。简历版本虽然包含 `fileId`，其他设备却没有对应的二进制文件，所以“原始文件”按钮可能显示存在，实际打开时才发现文件不可用。

当前“重新提取并排版”固定使用 `refreshRawText: true`。这会忽略已有 `rawText`，强制重新读取原件。在另一台设备没有本地原件时，原始文本明明存在，任务仍可能在 AI 调用前失败。AI 处理又把基础信息、候选人画像和电子简历排版放在同一个异常处理块中，最终只留下笼统的“简历 AI 处理失败，请重试”，无法判断失败阶段，也会把已经完成的阶段表现成整体失败。

## 目标

- 新上传的原始简历可以在同一 WorkBuddy 工作区的其他已授权设备上打开。
- 网络或云端文件上传失败时，候选人、原始文本、业务记录和历史版本仍然成功入库。
- 云端同步失败必须可见、可重试，不允许静默变成仅本机可用。
- 使用现有 `rawText` 的 AI 重试不依赖原始文件。
- 从原件重新提取时，依次尝试本机缓存、私有云端原件和兼容旧来源。
- AI 失败需要显示具体阶段和安全原因，并保留此前已完成的结果。
- 不删除或重建候选人，不改变推进记录、备注、负责人、分类、应用记录和其他历史版本。

## 非目标

- 不建设服务端 AI 队列；AI 任务仍在当前浏览器中运行。
- 不把文件二进制塞入工作区 JSON 快照或 `localStorage`。
- 不把简历原件放入公开 bucket，也不生成永久公开 URL。
- 不自动删除云端历史文件或实现完整文件生命周期清理。
- 不自动恢复只存在于其他设备本地缓存中的旧原件；旧文件必须从持有原件的设备补同步或人工重新上传。
- 不在本次改造中重构与简历处理无关的页面或旧 Gist 代码。

## 方案比较

### 方案 A：私有云端原件加本机缓存（采用）

新文件先写入 IndexedDB，再通过已有 Supabase 工作区客户端上传到私有 `workbuddy-files` bucket。简历版本保存云端对象路径和同步状态。其他设备在本机缓存缺失时下载云端原件并回填 IndexedDB。

优点是符合现有 Supabase 登录和工作区权限体系，文件不会进入大 JSON 快照，离线时仍可使用本机缓存。缺点是需要配置 Storage bucket 和 RLS，并处理本地成功、云端失败的中间状态。

### 方案 B：把文件转成 Base64 放入工作区快照（不采用）

实现简单，但会显著放大每次工作区保存、冲突合并和网络传输的数据量，也容易触及浏览器、数据库行大小和请求大小限制，与现有剥离大文件的设计相冲突。

### 方案 C：只保留当前设备本地文件（不采用）

开发成本最低，但无法满足跨设备查看，也会继续让 `fileId` 造成“元数据存在等于文件可用”的错误判断。

## 存储架构与权限

使用现有 `WorkBuddyWorkspace.createWorkspaceClient()` 中的 `uploadFile()` 和 `downloadFile()` 接口，bucket 固定为私有 `workbuddy-files`。浏览器只持有 Supabase publishable key 和当前登录会话，不使用或暴露 service role key。

云端对象路径使用不可预测的稳定标识，不使用候选人姓名和原文件名：

```text
workspace/main/resumes/<candidateId>/<versionId>/<fileId>
```

原文件名只保留在业务元数据中用于下载显示，避免姓名直接出现在对象路径和日志里。bucket 限制允许的简历 MIME 类型与单文件大小；客户端继续执行现有文件校验，服务端 bucket 限制作为第二道边界。

RLS 规则：

- 只有已登录且资料状态为 `active` 的工作区成员可以读取对象。
- 只有 `admin` 和 `editor` 可以上传对象。
- `viewer` 只能读取，不能上传、覆盖或删除。
- bucket 保持私有，读取使用带当前 JWT 的 `download()`。
- 本次使用唯一对象路径和 `upsert: false`，不授予覆盖能力。

Storage API 的底层错误需要保留安全错误码和状态用于诊断，但不得在 UI、日志或工作区数据中暴露 JWT、API Key、完整响应头或简历正文。

## 简历版本数据模型

在每个 `resumeVersion` 上增加或规范以下字段：

```js
{
  fileId: '',
  fileName: '',
  fileType: '',
  fileSize: 0,
  fileHash: '',
  cloudFilePath: '',
  originalFileStatus: 'local-only',
  originalFileError: '',
  originalFileSyncedAt: '',

  rawText: '',
  formattedText: '',
  aiStage: '',
  formatStatus: 'queued',
  formatError: '',
  formattedAt: ''
}
```

`originalFileStatus` 取值：

- `local-only`：本设备已经保存原件，但还没有云端副本。
- `syncing`：正在上传云端。
- `synced`：云端对象已经确认上传成功。
- `sync-failed`：本地原件仍在，但云端上传失败，可重试。
- `missing`：本机、云端和兼容来源均不可用。

`aiStage` 取值：`source`、`basic`、`profile`、`format` 或空字符串。它表示当前处理阶段或最后失败阶段。`formatStatus` 继续兼容 `queued | processing | done | failed`，避免破坏既有页面和快照。

兼容规则：

- 旧版本有 `cloudFilePath` 时按云端可读取处理。
- 旧版本只有 `fileId` 时不能直接断言原件可用；需要异步检查本机 IndexedDB。
- 旧版本有 `fileData` 或 `sourceResumeId` 时保留现有兼容读取。
- 不因字段缺失批量修改旧记录；在读取和用户操作时逐步补齐状态。
- `rawText`、`formattedText` 和现有文件引用原样保留。

## 新上传数据流

### 阶段一：可靠入库

1. 校验文件类型和大小。
2. 生成候选人、简历版本和 `fileId`。
3. 把原始文件写入当前设备 IndexedDB。
4. 提取并保存 `rawText`。
5. 保存候选人、版本元数据和业务记录，`originalFileStatus` 初始为 `local-only`。
6. 页面立即确认“已入库”，不得等待云端文件或 AI 完成。

如果 IndexedDB 原件保存本身失败，沿用现有上传失败规则，因为此时系统没有可靠原件。若候选人和文本已经完成持久化，后续云端或 AI 失败不得删除它们。

### 阶段二：原件云端同步

1. 将状态改为 `syncing` 并持久化。
2. 使用唯一 `cloudFilePath` 上传私有 bucket。
3. 成功后写入 `synced`、清空错误并记录 `originalFileSyncedAt`。
4. 失败后写入 `sync-failed` 和安全错误原因，保留本机 IndexedDB 文件及所有业务数据。
5. 成功或失败都通过保存协调器写入工作区并排队云端工作区状态同步。

同一版本的同步任务去重并串行化。重试使用相同路径；如果上传接口报告对象已经存在，应通过可读性校验确认对象存在后视为成功，而不是盲目覆盖。

### 阶段三：AI 处理

AI 默认直接使用已经持久化的 `rawText`，按基础信息、画像和排版顺序执行。每一步更新阶段、保存成功结果并清空该阶段旧错误。AI 队列不等待原件云端上传完成。

## 跨设备打开原件

点击“原始文件”时按以下顺序解析：

1. 如果 `fileId` 对应的 IndexedDB blob 存在，直接使用。
2. 如果存在 `cloudFilePath`，从私有 bucket 下载，校验返回 blob 后写入当前设备 IndexedDB，再打开预览。
3. 尝试旧 `fileData` 和 `sourceResumeId` 兼容来源。
4. 全部失败时把运行时可用状态标记为缺失，并显示明确恢复方式。

下载失败要区分未登录、无权限、对象不存在、网络失败和未知后端错误。网络失败不应永久把已同步元数据改成 `missing`；只有确认对象不存在且没有其他来源时才使用缺失状态。

“原始文件”入口不再只依据 `fileId` 显示为可用。页面展示以下状态：本机可用、云端可用、正在下载、仅上传设备可用、云端同步失败、原件缺失。按钮异步下载期间禁用，避免重复请求。

## 旧原件补同步

对于升级前上传的版本：

- 当前设备能从 IndexedDB 或旧来源读到原件时，显示“同步原始文件”，上传成功后写入 `cloudFilePath`。
- 当前设备只有 `rawText` 时，允许使用文本重新执行 AI，但不伪装成拥有原件。
- 原始设备也不可访问且云端无副本时，提供“重新上传原件”。重新上传只给当前版本补充文件引用和云端副本，不创建候选人、不清空结构化字段、不改动业务历史。
- 系统不在页面加载时扫描并上传全部旧文件，避免未经用户动作产生大量网络传输。

## AI 分阶段处理与重试

AI 处理器在每个外部步骤前设置 `aiStage`：

1. `source`：仅“从原始文件重新提取”模式使用。
2. `basic`：基础信息提取。
3. `profile`：候选人画像提取。
4. `format`：电子简历排版。

每一步成功后立即保存。后续步骤失败时保留已经写入的基础字段、画像字段和既有 `formattedText`。只有新的排版成功时才替换 `formattedText`。

页面提供两个明确动作：

- **使用现有文本重新处理**：要求 `rawText` 足够长，不读取原件，适合其他设备和原件临时不可用场景。
- **从原始文件重新提取并处理**：先按本机、云端、旧来源顺序取得原件，重新生成 `rawText`，再执行三项 AI 工作。

新上传后的后台 AI 使用第一种模式，因为上传阶段已经获得 `rawText`。这样原件同步失败不会阻塞 AI。

## 错误模型与页面反馈

处理器保存结构化错误，而不是只保存通用文本：

```js
{
  aiStage: 'format',
  formatStatus: 'failed',
  formatErrorCode: 'AI_TIMEOUT',
  formatError: '电子简历排版请求超时，请重试'
}
```

用户可见错误至少覆盖：无 AI 权限、Key 未配置或无效、请求超时、网络失败、限流或额度不足、AI 返回格式错误、原件不可用、原始文字过少、本地保存失败和云端文件同步失败。

错误文案包含阶段，例如“候选人画像提取失败：AI 返回格式错误”。原始异常只在经过脱敏后写入调试日志；页面和共享工作区只保存稳定错误码及安全文案。

当排版失败但已有 `formattedText` 时，继续展示上一次成功版本，并以非阻断提示说明本次更新失败。没有 `formattedText` 时才显示明确标识的“原始提取文本”降级内容。不得静默降级。

## 保存、一致性与恢复

- 候选人入库、文件同步状态和 AI 阶段结果都使用现有 `saveWorkbenchV2()` 及保存协调器。
- 文件同步和 AI 队列分别去重，二者都不能并行修改同一版本的同一状态字段。
- 所有更新都基于当前内存中的最新候选人和版本对象，不捕获并延迟写回旧快照。
- 刷新后，`syncing` 恢复为可重试状态；不会未经确认自动上传全部旧数据。
- 刷新后，AI `processing` 仍按现有待处理键恢复，但默认使用持久化的 `rawText`，不强制寻找原件。
- 文件上传成功而工作区状态写入暂时失败时，使用同一路径重试并通过对象已存在校验收敛到 `synced`。

## 安全要求

- bucket 必须是私有 bucket。
- Storage RLS 必须在部署前验证 reader/editor/admin 权限矩阵。
- 不在静态代码中加入 service role key、数据库密码或新的私密凭据。
- 不使用候选人姓名作为云端路径。
- 不在错误提示、控制台或遥测中输出完整简历正文。
- 预览继续遵守现有文件类型处理，不把下载内容当作可执行 HTML。
- 文件大小和 MIME 限制同时在客户端和 bucket 配置层执行。

## 测试策略

### 文件服务单元测试

- 本机有 blob 时不请求云端。
- 本机缺失且有 `cloudFilePath` 时下载并回填 IndexedDB。
- 云端网络失败不会误标为永久缺失。
- 云端对象不存在且没有兼容来源时返回可恢复的缺失状态。
- 上传失败保留 `local-only` 文件并写入 `sync-failed`。
- 重复同步同一版本只产生一个活动任务。
- 对象已存在且可下载时重试收敛为 `synced`。

### AI 处理单元测试

- 使用现有文本重试时完全不调用原件读取器。
- 从原件重试时按本机、云端、旧来源顺序读取并替换 `rawText`。
- `basic`、`profile`、`format` 任一步失败都保存准确阶段和错误码。
- 后一步失败不会抹掉前一步结果或上次成功的 `formattedText`。
- 无权限、无效 Key、超时、网络、限流和 JSON 错误生成不同安全提示。
- 刷新恢复不会把有 `rawText` 的任务强制切换为原件模式。

### 集成和界面测试

- 设备 A 上传后，候选人先入库；模拟云端上传失败时显示“原件仅本设备可用”和重试入口。
- 云端同步成功后，设备 B 可以下载、预览并缓存原件。
- 设备 B 只有 `rawText` 时仍能使用现有文本执行 AI。
- 两种重试按钮的含义、禁用状态和错误反馈清晰。
- 旧简历可以补同步原件，补同步前后版本 ID 和业务记录不变。
- viewer 能下载但不能上传；editor/admin 能上传和下载；未登录用户不能读写。

### 回归和上线验证

- 现有完整测试套件通过。
- 生产构建和内联脚本解析检查通过。
- 在真实浏览器验证新上传、断网入库、恢复同步、跨设备下载和分阶段 AI 失败。
- 在 Supabase SQL/Storage 策略层验证 RLS，而不只依赖前端角色判断。
- 部署后打开 GitHub Pages，验证实际资源版本、控制台、网络请求和跨设备行为，不能仅以构建或工作流成功作为上线依据。

## 验收标准

- 云端文件上传失败不会导致候选人、原始文本或业务历史丢失。
- 新上传原件成功同步后，在另一台已授权设备可打开。
- 页面不会仅凭 `fileId` 错误声称原件可用。
- 有 `rawText` 时，“使用现有文本重新处理”不依赖原始文件。
- AI 失败能明确显示失败阶段和原因，已经成功的阶段结果仍保留。
- 旧记录有明确的补同步或重新上传恢复路径。
- 任何修复都不删除原始文件、历史版本、推进记录、备注、负责人、分类或现有业务记录。
