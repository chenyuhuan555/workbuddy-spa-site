# IndexedDB 安全恢复设计

## 目标

修复 WorkBuddy 打开页面时出现“本地存储异常”以及人才简历解析成功后原始文件保存失败的问题，同时保留浏览器中已经存在的业务快照与简历文件。

## 已确认的故障链路

1. 原始简历解析成功后，`saveResumeBlob()` 向 IndexedDB 的 `files` store 写入 `Blob`。
2. 当前数据库版本为 5，打开成功后只校验 `appSnapshots`，没有校验 `files`。已经处于 v5 但结构不完整的数据库不会再次执行升级逻辑。
3. `saveResumeBlob()` 捕获所有异常并返回 `false`，调用层只能显示通用错误，无法区分结构缺失、空间不足、事务中止或多标签页阻塞。
4. 启动迁移在 hydration 期间直接调用 `localSave()`，绕过已有的防抖串行保存协调器。
5. `localLoad()` 遇到读取异常会删除主快照；瞬时数据库故障不应触发数据删除。

## 设计

- 将数据库版本从 5 无损提升到 6。升级事务只创建缺失的 `files`、`hash` 索引或 `appSnapshots`，不删除、不清空、不改写已有记录。
- 打开成功时同时校验两个 store；缺失时返回明确结构错误。增加 blocked/versionchange 处理，避免多标签页长期占用连接。
- `saveResumeBlob()` 成功仍返回 `true`，失败改为抛出保留 `name` 与具体消息的异常；批量和单份导入直接显示该错误。
- 启动阶段只在内存中执行旧数据补齐；云端初始化完成后，再通过 `saveCoordinator.markDirty('legacy')` 串行保存最终状态。
- 本地快照读取失败或结构不合法时保留原始存储，仅跳过本次恢复并记录警告。

## 数据安全边界

- 禁止调用 `indexedDB.deleteDatabase()`。
- 禁止清空或删除 `files`、`appSnapshots`。
- 不改变现有数据库名称、store 名称和记录 key。
- 不在保存失败时创建不含原始文件的人才记录。
- 回滚采用恢复部署前 Git 提交；v6 数据库仍与旧代码兼容，因为 store 与数据格式没有改变。
