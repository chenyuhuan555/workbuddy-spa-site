# WorkBuddy 前端隐藏失效推进设计

## 背景

推进记录会长期保留候选人与岗位之间的业务历史。当关联的公司或岗位已经删除时，推进中心当前仍展示这些记录，并回退显示“公司已删除 / 岗位已删除”。这些记录是用户明确不再需要参与日常业务的历史数据，但不能因此级联删除推进历史。

## 目标

- 在整个业务前端隐藏关联失效的推进记录。
- 将失效推进排除在分页、数量、看板和经营统计之外。
- 保留完整推进数据，继续支持保存、云同步、备份和管理员审计。
- 已关闭但仍存在的公司或岗位继续按正常记录展示。

## 非目标

- 不删除或软删除推进记录。
- 不修改推进阶段、负责人、匹配分、时间线或历史事件。
- 不增加“显示失效推进”的普通前端开关。
- 不改变公司、岗位或人才的删除规则。
- 不执行数据库结构迁移。

## 有效推进规则

新增一个纯函数模块，集中判断推进记录是否可进入业务前端。推进仅在以下条件全部满足时有效：

1. 推进记录本身存在有效 ID，且未标记删除。
2. `candidateId` 对应的人才存在，且未标记删除。
3. `companyId` 对应的公司存在，且未标记删除。
4. `positionId` 对应的岗位存在，且未标记删除。

公司或岗位的 `status` 为关闭、暂停等业务状态时不视为删除。只要实体仍存在且没有删除标记，推进继续显示。

## 架构与数据流

保留 `workbenchV2.applications` 作为完整、权威的推进集合。页面基于当前人才、公司、岗位索引计算 `visibleApplications`，再构造只供展示和统计使用的可见业务集合。

```text
workbenchV2.applications（完整原始推进）
├─ 保存、云同步、迁移、备份、修复审计
└─ 前端有效性过滤
   └─ visibleApplications
      ├─ 推进中心表格与阶段看板
      ├─ 公司、岗位、人才详情
      ├─ 搜索与分页
      ├─ 公司和人才推进数量
      └─ 首页指标、经营漏斗、面试与 Offer 统计
```

纯函数模块只负责：

- 根据人才、公司、岗位集合建立有效 ID 集合。
- 判断单条推进是否有效。
- 返回保持原顺序的有效推进数组。

模块不读取浏览器状态、不写入数据，也不触发保存或云同步。

## 前端接入范围

以下用户可见派生数据必须使用 `visibleApplications` 或包含该集合的展示专用业务包：

- 推进中心筛选、表格、阶段看板和分页。
- 候选人、公司和岗位详情中的推进列表与推进数量。
- 公司列表的活跃推进数与面试数。
- 人才活跃推进数和活跃人才汇总。
- 首页仪表盘、业务进展条、阶段统计、面试数和 Offer 数。
- 其他仅用于展示、搜索或汇总推进记录的派生视图。

以下路径继续使用完整的 `workbenchV2.applications`：

- 新建、修改和持久化推进。
- 云端双写、增量同步、迁移与一致性检查。
- 完整备份与恢复。
- 管理员数据修复和审计工具。

## 页面行为与异常处理

- 失效推进不显示占位行，也不计入前端总数。
- 不新增普通用户可见的恢复入口或隐藏数量提示。
- 如果关联集合尚未加载完整，采用安全默认值，不展示无法确认有效性的推进。
- 云端读取失败继续使用现有本地回退和同步错误提示，不新增另一套错误状态。
- 过滤过程不得修改原数组或推进对象。

## 测试与验收

### 单元测试

- 正常人才、公司、岗位关联的推进会保留。
- 缺失人才、公司或岗位的推进会隐藏。
- 人才、公司或岗位带删除标记时会隐藏。
- 已关闭但仍存在的岗位关联会保留。
- 输入顺序保持不变，原始数据不被修改。

### 接入测试

- 推进中心列表、阶段看板和分页使用有效推进。
- 公司、岗位、人才详情及数量使用有效推进。
- 仪表盘、经营漏斗、面试数和 Offer 数使用有效推进。
- 保存、云同步、备份和修复审计仍使用完整原始推进。

### 发布验收

- 完整测试、模块测试和生产构建全部通过。
- GitHub Pages 对目标提交构建和部署成功。
- 线上推进中心不再显示“公司已删除 / 岗位已删除”的历史推进。
- 线上相关统计不包含这些失效推进。
- 管理员数据审计仍可读取完整历史记录。

## 回滚

该变更不迁移或删除数据。出现问题时回退前端过滤提交即可恢复旧展示行为，原始推进记录始终保留。
